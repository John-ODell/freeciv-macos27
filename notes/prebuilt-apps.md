### 1.4 Signing / Gatekeeper (observed)
- `codesign -dvvv Freeciv.app` -> "code object is not signed at all"; same for `bin/freeciv-qt`, `bin/freeciv-gtk4`, `bin/freeciv-server`, `lib/libfreeciv.dylib`, and all 278 Homebrew dylibs (loop over `codesign -dvv`). REA `inspect_signature` (ev_4ff0e095…): `signed:false`, codesign exit 1 x3. No entitlements, no hardened runtime, no team.
- `spctl -a -vv -t exec Freeciv.app` -> `rejected`, `source=no usable signature`. `xcrun stapler validate` -> no ticket (not notarized).
- `xattr -l Freeciv.app` -> only `com.apple.provenance` (no `com.apple.quarantine`), so the Gatekeeper first-launch dialog was never triggered here (derived). The tar.gz was evidently fetched without a quarantining client.
- Gatekeeper on macOS 27 (inferred from the above): if the archive were downloaded with Safari/a browser, the bundle would be quarantined and, being unsigned and un-notarized, blocked with the "Apple could not verify ... is free of malware" dialog; since macOS 15 the only bypass is System Settings > Privacy & Security > Open Anyway (the ctrl-click/Open trick no longer works for unsigned apps). This matches what the author's README describes. Rosetta still runs unsigned x86_64 code; arm64 code must at least be ad-hoc signed, which is irrelevant here because there is no arm64 slice.

### 1.5 dyld resolution on THIS machine (REA `trace_dylib_resolution` ev_63889d4f… on freeciv-qt; manual closure script `closure.py` over all four roots; `otool -L`)
- REA finding (observed, basis "derived" in REA): `required-load-unresolved`: "No candidate for @rpath/libfreeciv.dylib exists in the analyzed root; dyld would fail to load this required dependency for freeciv-qt (x86_64)". `rpaths: []`. The 8 absolute `/Applications/...` loads are reported `outside-target / undetermined` by REA (it does not evaluate absolute paths); the closure script confirms all of them are MISSING here.
- Per executable (derived, closure script): freeciv-qt 8 of 10 deps missing (7 absolute `/Applications/...` + unresolved `@rpath`), freeciv-gtk4 13 of 14, freeciv-server 4 of 5, freeciv-mp-qt 5 of 8. Only `/usr/lib/libSystem.B.dylib`, `/usr/lib/libc++.1.dylib`, `/usr/lib/libsqlite3.dylib` resolve (dyld shared cache; `dyld_info` confirms they are in the cache though absent on disk).
- Why `@rpath/libfreeciv.dylib` can never resolve as shipped (derived): there is no LC_RPATH, so dyld's only remaining search is the fallback list, which for a minos 11 binary defaults to `/usr/local/lib:/usr/lib` (observed in `man dyld`: "For new binaries (Fall 2023 or later) there is no default. For older binaries, there is a default fallback search path of: /usr/local/lib:/usr/lib"). That is exactly what dyld printed: `tried: '/usr/local/lib/libfreeciv.dylib' (no such file), '/usr/lib/libfreeciv.dylib' (no such file, not in dyld cache)`. Even installed in /Applications it would only work if `/usr/local/lib/libfreeciv.dylib` exists (inferred: the packager's own machine had a Homebrew/`make install` copy there, which is why they never noticed).
- `LSEnvironment LD_LIBRARY_PATH` (observed in plist) is not a variable macOS dyld reads: `man dyld` documents only `DYLD_LIBRARY_PATH`, `DYLD_FALLBACK_LIBRARY_PATH`, etc. (observed: the only matches for "LD_LIBRARY_PATH" in `man dyld` are substrings of `DYLD_LIBRARY_PATH`). It has a side effect though: LaunchServices marks the app `requiresSecureLaunch` because of it (see 1.6).

### 1.6 Launch tests (observed)
**(a) Finder-style:** `open -W --stdout … --stderr … Freeciv.app` -> exit 1, stderr `_LSOpenURLsWithCompletionHandler() failed with error -54.`, both app log files empty, no process ever created, no crash report (`official-open.log`). -54 = `permErr` "permissions error (on file open)" (observed: `MacErrors.h:81`).
Unified log for that second (observed, `/usr/bin/log show --start '2026-10-15 22:29:34' --end …`):
- `lsd: Error -67062 validating the signing information for <private>, error=… Code=-67062 "(null)" UserInfo={SecCSArchitecture=x86_64}` (-67062 = `errSecCSUnsigned`, observed in CSCommon.h:84)
- `lsd: Marking <private> as .requiresSecureLaunch because it has a LSEnvironment item`
- `lsd: Failed to register <private> trusted: NSOSStatusErrorDomain/-67060` (-67060 = `errSecCSSignatureNotVerifiable`, CSCommon.h:86)
- `CoreServicesUIAgent: _LSLaunchRB(freeciv …) … LAUNCH: _LSLaunchThruRunningboard: freeciv`, after which `open` reported -54 and no `freeciv-qt` process appeared.
- `lsregister -dump` shows LS did resolve `executable: Contents/bin/freeciv-qt` and `execSDK ver: 11.3`, so the `../bin` path itself is parsed by LaunchServices.
Interpretation (inferred): the LS/RunningBoard "secure launch" path that LSEnvironment forces cannot validate the unsigned x86_64 executable and aborts with permErr before posix_spawn. Exactly which check returns -54 is **unknown** (the relevant RunningBoard lines are `<private>`); I did not alter a copy of the bundle to bisect it. What is certain is that even if LS had spawned it, dyld would have aborted as in (b).
**(b) Direct exec:** `Contents/bin/freeciv-qt` from zsh -> `Abort trap: 6`, exit 134, stderr `dyld[82414]: Library not loaded: @rpath/libfreeciv.dylib … Reason: tried: '/usr/local/lib/libfreeciv.dylib' (no such file), '/usr/lib/libfreeciv.dylib' (no such file, not in dyld cache)` (`official-direct.log`). Crash report `official-direct__freeciv-qt-2026-10-15-223053.ips`: `cpuType X86-64, translated: true` (Rosetta), `exception EXC_CRASH (SIGABRT)`, `termination namespace DYLD code 1 indicator "Library missing"`, reasons = the dyld message above, faulting thread 0, frames: `dyld abort_with_payload_wrapper_internal` <- `abort_with_payload` <- `dyld4::halt` <- `dyld4::prepare` <- `dyld4::start` <- `start` ("terminated at launch; ignore backtrace"). Only 2 images loaded (freeciv-qt, dyld).
**(c) Retry with DYLD variables** (exactly what I did, see `official-dyld-retry.env` / `official-dyld-retry.log`): ran `/usr/bin/env DYLD_LIBRARY_PATH=<Contents/lib + all 48 Contents/homebrew/Cellar/*/*/lib dirs> DYLD_FRAMEWORK_PATH=<Cellar/qt@5/5.15.8_2/lib> QT_PLUGIN_PATH=<Cellar/qt@5/5.15.8_2/plugins> FREECIV_DATA_PATH=<Contents/share/freeciv> Contents/bin/freeciv-qt`. (First attempt through my bash helper silently lost the DYLD_* variables because `/bin/bash` is a platform binary and dyld strips them from restricted processes - observed as the identical dyld abort; passing them as `env(1)` arguments fixed that.) Result: `freeciv-server --version` -> `Freeciv version 3.1.0-beta1`, `freeciv-qt --version` -> `Freeciv version 3.1.0-beta1 gui-qt`, and the GUI run printed only `3: Didn't find the option file. Creating a new one.` and a `qt.qpa.fonts` notice, stayed alive until I killed it at 60 s, no crash report. Screenshot `official-dyld-retry.png` shows the Qt5 main menu ("version 3.1.0-beta1, Qt5 client", Start new game / Connect to network game / …). The Qt cocoa platform plugin loaded (QT_PLUGIN_PATH), so Qt 5.15.8 x86_64 under Rosetta works on macOS 27. Note: the large "Freeciv (Qt6)" window behind it in that screenshot belongs to another session's own build running on this Mac, not to this app.
No `freeciv-gtk4` GUI test was run (not the bundle's CFBundleExecutable); its load commands have the same two defects (no LC_RPATH, absolute /Applications paths).

### 1.7 Conclusion for the official app
Failure classes: **(d) bundle layout and (a) dylib graph** are each independently fatal; **(c) signing** additionally blocks the Finder/`open` path; **(b) runtime/toolkit is not a problem** (demonstrated by 1.6c). Specifically: (1) CFBundleExecutable outside `Contents/MacOS` is tolerated by LaunchServices but combined with an unsigned x86_64 binary and `LSEnvironment` the secure-launch path refuses it with -54; (2) `LSEnvironment LD_LIBRARY_PATH` is ignored by dyld; (3) `@rpath/libfreeciv.dylib` with zero LC_RPATH entries can only be satisfied by `/usr/local/lib` or `/usr/lib`; (4) every other dependency and every `homebrew/opt` symlink is an absolute `/Applications/Freeciv.app/...` path, so the bundle is non-relocatable; (5) it is x86_64-only (Rosetta required). Even copying it to /Applications (not done, per instructions) would still hit (3).
